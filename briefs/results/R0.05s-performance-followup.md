# R0.05s performance follow-up — diagnosis, not a demonstrated fix

28 September 2026. The user reported that the latest portaloo build felt very slow. Work on new features was paused. This follow-up compares the shipped R0.05s export with the prior accepted R0.05r export, then measures actual toilet service in a separate diagnostic export. **The user-visible slowdown is not yet reproduced in the awake controlled runs, so no gameplay/rendering setting was changed and no replacement performance build is claimed.** The user has been asked for the slow run's phase, resolution/display and power state.

## Controlled conditions and results

The exported profile uses Godot 4.7.2 GL Compatibility on the NVIDIA GeForce RTX 3050 Ti Laptop GPU (driver 596.08), 32 people/9 performers, VSync enabled and the unchanged 58 FPS cap. The same scripted 50-second path covers stationary-camera, pan, quarter-turn rotation and zoom phases at 1280×720. It starts the normal booking campaign and records frame intervals, C# callback/simulation/presentation time, allocation/GC counts, focus and exact final current-version save/reload. The stationary-camera phases still call `ApplyCamera()` each frame; these are not untouched ordinary idle. Runs used one hidden exported process at a time, all recorded frames focused, with empty stderr.

| Export / state, 720p | Frames in 50 s | Final tick | Warm p50 / p95 / p99 ms | Warm >50 / >100 ms | Longest warm frame |
|---|---:|---:|---:|---:|---:|
| R0.05s, slow interval | 506 | 4,398 | 8.53 / 258.81 / 265.26 | 174 / 174 | 283.31 ms |
| Prior R0.05r, same slow interval | 495 | 4,363 | 8.56 / 260.05 / 265.46 | 174 / 174 | 269.24 ms |
| Prior R0.05r, later awake repeat | 2,889 | 5,804 | 17.21 / 23.97 / 26.45 | 0 / 0 | 38.16 ms |
| R0.05s, later awake repeat | 2,887 | 5,802 | 17.20 / 24.23 / 26.68 | 0 / 0 | 39.71 ms |

The slow intervals were not unique to portaloo code: the previous executable stalled identically. All 174 warm >100 ms intervals in each slow run fell **outside** the C# callback. A separate 720p preparation profile with VSync on ran 2,893 frames, p95 21.61 ms, with only one cold >100 ms frame. A later correctly launched 1080p R0.05s live VSync-on run was smooth (2,885 frames, warm p95 24.17 ms, zero warm >50 ms). Turning VSync off after the slowdown also produced smooth 720p/1080p runs, but VSync-on repeats after the same point were equally smooth. Therefore changing VSync would be an unsupported and potentially tear-inducing response; the project default remains unchanged.

Windows Kernel-Power events show entry into Modern Standby at 14:26:50 and exit at 16:18:24 local. The two slow profile files were written during that long standby interval; the smooth repeats were after wake. However an older smooth R0.05r profile was also written during a separate, shorter standby interval, so standby is a **confounder, not proven sole cause**. The available timing does not establish whether the user's visible run encountered the same condition. No processes unrelated to these exact diagnostic launches were stopped and no global graphics or power settings were changed.

## Toilet-active check

An opt-in `live-toilet` camera-profile mode was added to `game/Main.CameraProfile.cs`. It starts the same normal campaign, then labels two guests as high-need/low-thirst *only for the profile*, so toilet service occurs inside the measurement window. The fixture records occupancy/queue alongside frame intervals and verifies current-version final save/reload. An independent reviewer confirmed that it completed two physical wee visits, reached queue length two and did not modify normal gameplay. The reviewer caught a callback-attribution error: the fixture's per-frame `CaptureToilet()` was initially after the timing sample. It was moved before the sample and the reviewed diagnostic export was rerun. The profiler's pre-existing frame-record append still falls after the sample; do not interpret callback allocation as all profiler overhead.

| Reviewed toilet-active export | Total frames / final tick | Occupied frames | Warm p50 / p95 / p99 ms | Warm >50 / >100 ms | Longest warm frame |
|---|---:|---:|---:|---:|---:|
| 1280×720 | 2,863 / 5,802 | 613 | 17.23 / 24.36 / 28.20 | 0 / 0 | 48.19 ms |
| 1920×1080 | 2,878 / 5,801 | 619 | 17.19 / 24.43 / 28.66 | 0 / 0 | 35.52 ms |

Both runs report two wees, zero poos, and an exact current-version final save/reload. The 720p occupied and nonoccupied warm groups separately had zero >50 ms frames; the cold 212 ms maximum happened before occupancy. This does not prove every organic need pattern, maximum zoom, visible-window/compositor state, battery mode or user-specific scene is fast. The diagnostic export under `artifacts/windows/r005t-profile-diagnostic/` is **not** a new game handoff or performance fix; the reviewed R0.05s executable remains the handoff.

Evidence is under [`reports/evidence/R0.05t-performance`](../../reports/evidence/R0.05t-performance/), with the two original slow profiles in [`reports/evidence/R0.05s`](../../reports/evidence/R0.05s/). Each new run's raw `profile.json` is losslessly retained as a verified `profile.zip` to avoid a half-million-line evidence commit. The final reviewed diagnostic profile logs have exit 0 and empty stderr. `dotnet build FestivalTycoon.sln -c Debug --no-restore` and `-c Release --no-restore` passed with zero warnings/errors; direct filtered toilet/current-save regressions passed 16/16; `git diff --check` found no whitespace error. The independent focused review found no evidence of a large toilet-specific hot path and rechecked the instrumentation correction. Superseded generated trial runs were removed; the reviewed controls remain.

## Open reproduction

No evidence-backed production performance change is justified yet. To reproduce the user's slowdown, obtain the exact build path, phase (preparation/live/after a visit), approximate elapsed play time, viewport/display resolution, camera zoom/action, whether the game window was foreground and visible, and plugged-in/battery or recent sleep/wake state. If a visible awake run is still slow, capture a matching profile/trace under those conditions and compare that run with the prior export before repairing. Do not present the transient slow hidden-window profiles as a portaloo regression or the smooth scripted fixture as final user acceptance.
