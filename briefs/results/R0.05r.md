# R0.05r — camera hitch profiling and bounded correction

28 September 2026. Scope: the reported frequent live hitches, especially noticeable while moving the camera. No art, crowd cap, rendering preset, engine, gameplay timing, or save-format change. This result uses the current-version save contract only.

## Finding and correction

The same 50-second deterministic camera path (cold idle, warm idle, pan, quarter-turn rotation, zoom, warm idle) was run in isolated Windows Release exports before and after the change. The fixture was the current 32-person/9-performer booking campaign, seed `20260922`, at 1280×720 on NVIDIA GeForce RTX 3050 Ti Laptop GPU, Godot 4.7.2 `gl_compatibility`, VSync enabled, 58 FPS cap; every recorded frame reported focus. The baseline's eight warmed >100 ms live frames occurred in all idle/movement phases and aligned with edition-boundary autosaves, not uniquely with camera motion. A save-stage diagnostic measured median 34.44 ms for boundary restore and 163.14 ms for boundary save; within the save, temporary/prior full validations each took about 68 ms. The atomic save checks remain intact.

The normal runtime now captures the authoritative persistence snapshot on the main thread, stages/advances/writes/validates the boundary in a worker, and publishes the saved candidate once on the main thread. The source session stays unchanged while pending; camera/presentation continue, non-camera commands and manual save/load/new campaign are refused during the transaction, and periodic autosave is suppressed until it finishes. The clock accrues bounded debt while waiting; only scheduled ticks *after* the worker-owned boundary tick are requeued. Failed writes leave the visible source and prior autosave intact and block advancement with a retry/load message. Shutdown joins the outstanding transaction. Opt-in diagnostics record frames and save stages; no logging is performed in the measured frame loop except in-memory samples.

The corrected warm live maximum was 31.74 ms in warm idle, 30.68 pan, 38.11 rotation, 34.87 zoom and 34.31 idle-after, versus baseline maxima 221.95, 212.32, 230.78, 228.72 and 220.17 ms respectively. The p99 slightly worsened (26.271 → 27.734 ms); this is a long-tail stall correction, **not** a blanket FPS increase. Different completed ticks in fixed wall time are not an exact-rate comparison: one run had more long blocking stalls. The new exact elapsed-input clock/coordinator test compares both implementations through two boundaries, pending time, pause and 4× speed, and reaches identical ticks and authoritative hashes.

Preparation control warm p50/p95/p99/max was 17.236/21.460/22.611/26.505 ms at baseline, and 17.237/21.494/22.656/25.647 ms on the corrected export; neither had a warm >33.333 ms frame. Both exported corrected profiles completed with exact current-version final save/reload hashes. Cold-start outliers remain (live overall max 187.930 ms; preparation 169.422 ms), and the sample is one machine/settings/campaign, not general performance or input-latency certification. Main-thread allocation sampling does not capture worker allocations; warmed main-thread allocations were about 6.1 GiB in each live run, with GC counts recorded in the raw profiles, not a demonstrated memory improvement. The normal five-minute periodic autosave remains synchronous and was not exercised by this 50-second window; it may warrant separate measurement if a later hitch report persists.
