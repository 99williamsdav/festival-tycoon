# Classic stress architecture review

Read-only architecture assessment of the commissioned scope at supplied baseline `7e969c62`, 15 October 2026. No implementation, tests, build, native run, export or PR performed. This is a pre-implementation review, not acceptance of a future diff.

## Highest-risk findings

1. **Unlimited must mean no instance quota, not enumeration of an unlimited quota.** `BuildLayout.cs:307` enumerates the entire per-kind limit to validate numbered IDs; `game/Hud/BuildDrawer.cs:318` materializes every possible van ID. Returning `int.MaxValue` alone makes these paths unusable. Parse canonical positive suffixes directly; UI should enumerate placed vans plus one next available van. Retain existing Survival static helpers, introduce explicit Classic instance policy, and thread it through command validation, previous-layout fit/cache key, current save validation and completed-history layout validation. `BuildLayout.cs:169` and `ClassicCampaign.cs:102` currently validate carried layouts against fixed tier-one/stage rules. Costs, collision, rotated approach and route checks must remain effective.

2. **Multiple response buildings currently do not exist as functional facilities.** `NextBuildId` returns only `first-aid` or `steward-post`; identity validation accepts only those literals. `Facilities.cs:45–49` selects the first building of each kind. `StaffFoundations.cs:28–31` sends all workers to one post, using only baseline-versus-extra offsets. `MedicalIncident.cs:101–126` supplies one rest centre. Allowing extra IDs without changing these consumers buys cosmetic duplicates.

   Recommended bounded design: preserve canonical first IDs and legacy single-post behavior; use numbered additional IDs and collection helpers for Classic. Each first-aid building must contribute actual reachable rest places, and rest selection/occupancy/recovery/guide-to-rest validation must recognize all those places. Existing hired workers can choose among real posts by a deterministic role-specific home policy; extra buildings must not manufacture staff, contracts, role slots, wages or response capacity. With fewer workers than posts, unstaffed posts should be honestly represented, while remaining usable destinations for those existing workers under the chosen policy. A nearest eligible post on return is one possible policy, but it must be specified and consistently used by arrival, return, drinking, route validation and UI.

   Collection audit: `ResponsePostPlacement.cs` reserved footprints, access checks and persisted footprint validation; `BuildLayout.cs` rest reserves and essential destinations; `Immersion.cs:119–131`; `VendorQueueGrowth.cs:44–48`; `MedicalIncident.cs` rest selection and rest validity; `Activities.cs:427`; `StaffInterventions.cs:59,170,195`; world post rendering and labels. Preserve fallback locations only for the same legacy states that use them today. Do not reinterpret the first lexical extra as a new canonical post accidentally.

3. **100 attendees is not a 100-person festival.** `SurvivalBalance.MaxActivePeople` and public `GameSession.MaxActivePeople` are 100, but `Preparation.cs:575` and `LifecycleKernel.cs:210` apply that limit to the entire roster. Three stages already imply 27 performers plus engineers and other staff. `Preparation.cs:259` also uses the cap when hiring extra response staff. Introduce distinct attendance and complete-roster bounds resolved from persisted Classic diagnostic state; keep Survival's constants and admission rules unchanged. Audit `NextFestival.cs:21` money-envelope bounds and all occurrences of `MaxActivePeople`, rather than simply increasing the shared constant.

4. **Three-stage support is partial; the main obstacle is setup and hiring, not live-loop array syntax.** Most live performance, power and activity loops already iterate stage count. `CampaignSetup.cs:200–222` creates exactly one additional engineer, nine performers and one generator at index 1. `Preparation.cs:190,225`, `StaffHiring.cs:79`, and `Main.StaffPanel.cs` expose only one extra-sound role/category. Every active stage needs a valid engineer assignment/contract and unique performer IDs without broadening medic/steward hiring limits. `MultiStage.cs:90` reconstructs saved stages from tier/pond only; `_diagnosticStages` by itself cannot round-trip. `BarnStage.cs` currently substitutes Barn for the second stage; it is not a three-stage constructor.

   Persist a Classic-only ordered active-stage selection, reconstruct it before roster/programme/weather/navigation validation, and keep available versus active stages distinct. Optional Barn and Pond mean stage-count-dependent 3/6/9 slots, not nine mandatory bookings while stages are inactive. Review `Main.Power.cs:96,107`, `Hud/TopBar.cs:345`, `Hud/BoxOffice.cs:246` for presentation that only names or displays stage 1. `BookingPanel`'s two changeover labels are correct for three slots per stage, not evidence of a two-stage limit.

5. **Demand cannot be expanded by dropping nine popularities into the existing formula.** `ClassicTicketDemand.cs:48` accepts at most three popularities and weights three values 60/25/15. `ClassicBooking.cs:63` expects three slots; the ledger constructor/validator fixes capacity at 25 (`ClassicBookingLedger.cs:39,69`), and replay resolves ticket counts at line 89. Existing demand behavior must remain identical for ordinary Classic. The diagnostic requires an explicit, persisted policy for presenting a multi-stage lineup to normal demand; do not silently change its weighting. A guaranteed-100 option must participate in deterministic ledger replay and wallet/roster validation; assigning the roster or wallet after confirmation creates an invalid save/accounting history. Persist separate guaranteed-admission and cash-grant provenance, with both defaults off.

6. **Isolation must cover saves, replay and history, not only the launch button.** `game/Main.Classic.cs:13–16,42` owns one ordinary Classic directory and cached host. Use a distinct diagnostic directory/host and visible persistent diagnostic identity. Every restart, continue, next edition and save rehydration must preserve that identity; reject diagnostic fields on Survival/Survival Steward snapshots. A synthetic reputation of 40/100 must not fabricate actual previous clears, carry assets, cash or band relationships. Reuse genuinely recorded Classic history only through a defined snapshot/copy boundary, with provenance; label the synthetic rating target honestly. The first actual two-star threshold being 14 must not be rewritten to make 40 appear earned.

## Review boundaries for implementation

- Construction quota removal applies to all Classic construction kinds, not merely this diagnostic entry point, according to the supplied commission. Normal Classic demand stays unchanged.
- Required narrow evidence includes multiple posts with functional destinations and unchanged staff count; high-number canonical IDs without quota-sized iteration; move/remove/save/load/carry with repeated facilities; 100 guests plus full three-stage crew; all optional stage combinations; nine contracts and unique performers; per-stage generators/engineers; deterministic replay with both diagnostic options independently on/off; isolated ordinary and diagnostic continuation.
- Preserve Survival/Survival Steward through explicit ruleset gating and existing parity/compatibility checks. Shared refactors are possible but must retain the legacy branch, IDs, order and default serialization behavior. This report has not executed those checks.

No architectural blocker prevents the commission, but response-post semantics and multi-stage booking demand semantics must be explicit before claiming functional completion.

## Follow-up: every stage optional, including Trailer (15 October)

The approved defaults now include synthetic reputation 40, genuine recorded first-clear carry from seed 20260922 (two stars, £261.90, three actual learned relationships), and both guarantee-100 and £1500 top-up off. This follow-up addresses Barn-only/Pond-only operation, not implementation acceptance. Working files were inspected during construction work; line references are navigation aids and may move.

**Recommendation:** use an active-only stage list in fixed catalogue order, with no placeholder closed-stage programmes or performers. Separate two meanings currently conflated in index zero: (a) first active programme/primary sound hire and (b) the physical Trailer/farm circuit. The former may remain ordinal; the latter must use stage identity. For the smallest coherent change, retain the farm generator as the existing site supply for stalls/lights, contribute zero Trailer rig draw when Trailer is closed, and create one existing-type stage generator for each active Barn/Pond regardless of its list index. Thus Barn-only has farm site supply plus Barn's own generator, rather than silently transferring Barn to the farm circuit. This preserves existing infrastructure/pooling semantics without requiring a new generator ownership model. It must be labelled accordingly in power UI.

`CampaignSetup.cs:194` always constructs the Trailer programme from all initial performers. Build an active programme roster directly, or replace/remove all corresponding initial performer/engineer/wallet/medical records before deriving any navigation or accounting state. Do not hide closed bands while retaining them as protected people. Completed save validation must derive expected performers as nine per active stage, and engineers as one per active stage, with closed stage IDs absent from the active programme and roster associations.

Do not globally redefine every no-argument programme call as first-active without checking physical presentation: `Main.StageSet`, Trailer world cues and Trailer actor/audio consumers can otherwise animate the Trailer to Barn-only music. Generic HUD and booking should use primary-active; venue rendering should always pass its own identity. `FestivalAudio.EnsureStage` allocating an idle Trailer audio player is not itself a fake band roster, but playback must follow actual active programmes.

Minimum coherent selection lifecycle: allow changing active stages during unconfirmed booking, rebuild stage-dependent draft state coherently, and freeze the active list once tickets/contracts are confirmed (or implement an explicit rebooking transition). Require at least one active stage before confirmation/opening; if an empty preparatory selection is allowed, guard all `Stages[0]`, maximum-duration and empty-programme accesses. This does not imply a music-free festival feature.

Validation cases for subsequent implementation review: all seven nonempty subsets of Trailer/Barn/Pond; own-generator isolation at active index zero; farm repair with a non-Trailer at zero; no closed-stage performers/contracts; correct stage-specific engineer destination; Pond-only weather exposure; Barn-only booking/HUD/audio/venue visibility; save/load retaining stage selection and circuit ownership. Keep all Survival/Survival Steward resolution on the original ordered Trailer-first path and preserve its saved representation.
