# M0.03 result — Validated content and scenario loading

Status: Accepted on 8 September 2026. Implemented and self-verified by Codex on Windows x64, then independently reviewed by Astra Low after one repair round.

## Scope and boundary

- `Festival.Simulation.Content` owns parsed input records, validation, immutable resolved definitions and canonical content hashing. It contains no disk or JSON APIs.
- `Festival.ContentAdapter` is the disk/JSON boundary. It reads one file, converts parse/read failures to diagnostics and passes the parsed document to the simulation loader.
- Schema version 1 includes only M0 dimensions, blocked cells, spawn/target locations, agent seed/count and one referenced service shape with duration, integer-penny price and stock.
- Stable service, scenario and location IDs are ordinal strings. Catalogue, scenario and service definitions have positive version fields.
- Successful loading resolves each scenario's service ID once to the same immutable `ServiceDefinition` instance. Collection storage is copied and exposed read-only.
- Any validation or adapter diagnostic produces a `ContentLoadResult` with a null catalogue. No `GameSession` is constructed by this content path, so invalid input cannot leave a partial active session.
- `services`, `scenarios`, `blockedCells` and `locations` are required JSON arrays. Empty arrays are structurally valid (subject to scenario spawn/target and reference rules); null, omitted arrays and null entries are rejected with the owning record plus an indexed field where applicable.

## Schema example

This abbreviated version-1 document shows the supported shape:

```json
{
  "schemaVersion": 1,
  "catalogueVersion": 1,
  "services": [
    { "id": "service.water", "version": 1, "durationTicks": 120, "pricePennies": 0, "stock": 100 }
  ],
  "scenarios": [
    {
      "id": "scenario.single-agent",
      "version": 1,
      "width": 8,
      "height": 8,
      "blockedCells": [{ "x": 4, "y": 2 }],
      "locations": [
        { "id": "spawn.gate", "kind": "spawn", "x": 0, "y": 3, "required": true },
        { "id": "target.water", "kind": "target", "x": 6, "y": 3, "required": true }
      ],
      "agentSeed": 101,
      "agentCount": 1,
      "serviceId": "service.water"
    }
  ]
}
```

The authored valid fixture contains single-agent, 50-agent and blocked-passage scenarios. The blocked-passage wall has one open cell; navigation/path existence is deliberately not evaluated before the navigation brief.

## Canonical content hash

The SHA-256 input is fixed binary data containing schema/catalogue versions and explicit collection counts, followed by:

1. services sorted by ordinal ID, with ID, version, duration, price and stock;
2. scenarios sorted by ordinal ID, with ID, version, dimensions, seed, count and resolved service ID;
3. blocked cells sorted by X then Y; and
4. locations sorted by ordinal ID, with kind, coordinates and required flag.

File path, JSON whitespace, JSON property order and authored ordering of semantically unordered arrays are excluded. All supported tuning fields are included.

## Acceptance mapping

1. `ValidFixtureLoadsTwiceWithSameHashAndResolvedReferences` loads the authored fixture twice, compares hashes, checks all three scenarios and proves the scenario references the catalogue's resolved service instance.
2. `ReorderingUnorderedRecordsDoesNotChangeHash` reverses services, scenarios, blocked cells and locations and obtains an identical hash.
3. `RequiredInvalidCategoriesAreActionableAndProduceNoCatalogue` covers duplicate IDs, missing references, invalid dimensions, nonpositive duration, negative quantities and unknown schema version. It requires file/record/field context for every category and a null catalogue. `InvalidJsonReturnsContextWithoutThrowing` covers adapter parse failure.
4. `MeaningfulTuningChangeChangesHash` changes service duration by one tick and obtains a different hash.
5. `OutOfBoundsSpawnAndRequiredTargetAreReported` and `BlockedSpawnAndRequiredTargetAreReported` require two contextual diagnostics in each case and a null catalogue.

## Independent review repair round 1

The reviewer reproduced a P1 `NullReferenceException` when otherwise valid JSON supplied null top-level/nested collections or null collection entries. The repair adds structural validation before record validation and resolution. `NullCollectionsAndEntriesReturnDiagnosticsThroughJsonAdapter` writes and loads twelve real JSON variants covering `services`, `scenarios`, `blockedCells` and `locations` as null, omitted, or containing null entries. Every variant now returns `IsSuccess=false`, `Catalogue=null`, and a `null_collection` or `null_record` diagnostic with file, owning record and field/index context. The post-repair build, all 18 tests and demonstration passed.

## Limitations and future constraints

- Path connectivity and reachability through the blocked-passage fixture await navigation; M0.03 validates only dimensions and usable location cells.
- Localized presentation keys, prerequisites, phase availability, feature flags, unlock cycles and contradictory exclusivities await their owning content systems.
- Agent instantiation, service queues, money/stock mutation, session integration, persistence and migration are outside this brief.
- The hash is a same-schema content identity, not a cross-schema compatibility promise.
- Manual QA was command-line only because this brief adds no visual behavior.
- M0.04 was not started.
