# M0.02 result — Deterministic clock, IDs and commands

Status: Accepted on 7 September 2026. Implemented and self-verified by Codex on Windows x64, then independently reviewed by Astra Low with no actionable defects.

## Scope and contracts

- Authoritative time is an integer festival tick of 250 milliseconds. `AdvanceTicks(count)` executes every tick and never consumes wall-clock delta. A paused session ignores advance requests completely.
- `CampaignId`, `EntityId` and `CommandId` are stable unsigned 64-bit values. Fixture entity allocation begins at 1 and increases monotonically; `NextEntityId` is authoritative and hashed.
- A `CommandEnvelope` carries command ID, campaign ID, expected phase, current target tick, submission sequence, optional target ID and typed command payload.
- `Execute` validates in this stable order: accepted-command duplicate, campaign, phase, tick, exact next submission sequence, then command parameters/target. Rejected commands do not mutate state or consume a submission sequence. Accepted commands apply immediately at the current deterministic boundary and are appended in invocation/submission order.
- Stable `CommandReasonCode` values are explicit: Accepted=0, DuplicateCommand=1, WrongCampaign=2, WrongPhase=3, WrongTick=4, OutOfOrderSubmission=5, UnknownTarget=6, InvalidParameter=7 and UnknownCommand=8.
- The only authoritative fixture commands are create record, change record value and pause/resume. They are documented in code as development fixtures. No player-facing domain model was introduced.
- Requested speed (1x/2x/4x) is captured state for the future scheduler but does not control explicit tick advancement. It is non-authoritative for checksum purposes, matching the verification rule that speed changes cannot change final simulation state.

## Random streams

The generator is `pcg32-xsh-rr-v1`: 64-bit PCG state/odd increment with XSH-RR 32-bit output. Each stream derives its state and increment only from the unsigned 64-bit campaign seed and its stable numeric `RandomStreamId`; it never uses object hashes or global randomness.

Owned streams are Demand=1, Weather=2, ForecastError=3, ArtistDecisions=4, IndividualBehaviour=5, Incidents=6 and Cosmetic=100. Consuming one stream cannot advance another. All non-cosmetic stream states and increments are included in the authoritative hash. Cosmetic state is deliberately excluded.

## Canonical hash membership

Canonical state is written in a fixed binary order and hashed with SHA-256. Schema version 1 includes:

1. hash schema version, tick duration and PRNG algorithm/version;
2. campaign ID and seed, session phase, current tick and paused state;
3. next entity ID and next accepted-command submission sequence;
4. fixture records sorted by entity ID: ID, value, remaining ticks and expired flag;
5. accepted command IDs sorted numerically;
6. applied command history in submission order: ID, tick, sequence, command type and affected target;
7. every non-cosmetic random stream sorted by stable stream ID: ID, state and increment.

Excluded: wall-clock/timestamps (none are stored), Godot/presentation state, requested display speed and the cosmetic random stream. Transient returned events are derived from state transitions and are not retained/hash members.

## Acceptance mapping

1. `SameSeedAndCommandsProduceIdenticalIntermediateAndFinalHashes` compares initialized, tick-100 and tick-400 hashes across two independent sessions. The runner independently repeats the full fixture.
2. `FourHundredTicksAreIndependentOfBatchSizes` compares one `AdvanceTicks(400)` call with repeating 1/7/32 calls; final hashes above match, tick is 400, and the scheduled record expired.
3. `PauseStopsTicksAndExpiryButAllowsValidCommands` proves 200 requested ticks leave the tick, expiry counter and hash unchanged while paused, then changes the target value at the same tick without progressing its counter.
4. `WrongPhaseAndUnknownTargetRejectWithoutMutation` asserts stable reason codes and byte-identical pre/post hashes for both failures.
5. `EqualTickCommandsUseSubmissionOrderAndAcceptedIdsAreIdempotent` asserts sequences 0/1/2/3, final value from the later equal-tick command, DuplicateCommand on resubmission, and unchanged post-duplicate hash/value.
6. `CosmeticAndUnrelatedStreamsDoNotPerturbBehaviourStream` consumes cosmetic and Weather streams in one session, then obtains the same eight IndividualBehaviour values as an untouched same-seed session. It also proves cosmetic consumption leaves the authoritative hash unchanged while Weather consumption changes it.

Additional coverage proves requested speed does not advance time or affect the authoritative hash, and entity IDs allocate monotonically with allocation state represented in the hash.

## Limitations and stop boundary

- This is same-build/content/settings determinism only; no cross-version replay claim is made.
- Session phase is the minimum Live/Egress enum needed for phase validation; no phase-transition or campaign-year behavior is implemented.
- The fixture record/counter is test and runner support, not game content.
- No real-time scheduler, world scene, needs, money, navigation, persistence or disk save was added. Stream capture/restore belongs to the future persistence brief.
- Manual QA was limited to command-line demonstration because M0.02 has no visual behavior.
- M0.03 was not started.
