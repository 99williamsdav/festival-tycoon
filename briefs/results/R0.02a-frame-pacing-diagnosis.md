# R0.02a frame-pacing diagnosis — decision memo

Status: **diagnosis, profiler-control test, and one native trace attempt; no fix accepted or attempted.** Compiled 24 September 2026 after the user requested an overview and independent Astra High input. R0.02a gameplay repairs passed focused re-review, but its VSync-on performance gate remains failed. The approved native trace attempt did not reproduce the recurring tail; do not infer authorization for a renderer change, timing-contract change, or R0.03.

## System in brief

- Godot 4.7.2 .NET on Windows x64, Compatibility/OpenGL, windowed 1280×720, NVIDIA RTX 3050 Ti Laptop GPU. The current project default is VSync **Enabled**, `run/max_fps=58`.
- Godot calls `Main._Process(delta)`. The presentation route passes that engine-provided delta to `FoundationClock`, which schedules the deterministic simulation at **80 authoritative ticks/s**, at most 16 ticks per callback. The game then updates people, equipment, stage visuals/audio and HUD. Boundary/periodic saves can synchronously hitch, but cannot explain a sustained repeated tail without corresponding in-callback work.
- The opt-in performance harness records wall time between callback endpoints, managed callback time, and their difference (`OutsideCallbackMs`), plus Godot's render CPU/GPU query, engine delta, ticks, focus and settings. Outside-callback time includes native engine/render/present/wait work and a short previous-callback instrumentation tail; it is not itself a GPU measurement. All existing runs enabled native viewport render-time measurement, a potential instrumentation confound.

The Release run used a separate fresh export in `artifacts/windows/r002a-release-check/`; the existing executable was not overwritten. The off/60 run was temporary and restored the project setting afterward. The user has already rejected visible tearing with VSync disabled, so it is not an acceptable default by itself.

In the current Enabled/58 Debug and Release runs, the 230 long frames averaged about **253 ms wall time**, with about **249 ms outside the managed callback** and only about **3.5–4.0 ms inside**. Godot reported only **36.43–36.47 seconds of total `_Process` delta** during **60.14–60.17 seconds of wall time**. With no clock-overload frames and less than one tick of reported debt, `FoundationClock` kept up with the time it was given; roughly **23.7 seconds were absent before scheduling**. The engine delta is therefore a propagation mechanism for 0.606× simulation speed, not the identified root cause of the native frame stall. [Godot documents a capped `_Process` delta](https://docs.godotengine.org/en/stable/classes/class_node.html#class-node-private-method-process), but the precise cap/smoothing path in these samples has not been traced to engine source.

The stalls begin by tick 9–10 and approximately 0.2–0.3 wall seconds in the current runs. **191/230 Debug** and **190/230 Release** long frames occur before the live music begins at tick 2400. Music playback, instrument attachment and live lights cannot be the initial trigger. Tier 1 (25 people) and Tier 2 (45) both show about 0.60×, weakening a simple crowd-size/managed-CPU explanation. Cheap reported render queries do not rule out driver/native synchronization during presentation or instrumentation elsewhere. The earlier R0.02 Enabled/58 pass is genuine, so a fixed VSync/cap setting is not robust on this machine under all observed states.

## Astra High independent assessment

1. **High confidence in a VSync-linked native presentation/pacing subsystem; low confidence in the exact component.** Engine, GL driver, Windows compositor/display routing or a timing-sensitive interaction could account for the fixed-length waits and on/off contrast. The measurements do not identify a particular Godot bug or prove the new audio/simulation is causative.
2. **Medium confidence in cap/display-refresh/VRR or window-state interaction.** Actual monitor refresh, VRR state, display routing and driver profile were not captured. Godot's [below-refresh cap guidance](https://docs.godotengine.org/en/stable/classes/class_projectsettings.html#class-projectsettings-property-application-run-max-fps) specifically discusses VRR; it does not establish why 58 helped one earlier run and failed now.
3. **Profiler/native GPU-timing interaction was a low-to-medium-confidence candidate and has now failed a controlled on/off test.** The persistent long gaps did not diminish when `ViewportSetMeasureRenderTime` and its render-time getter calls were disabled. This instrumentation is not the recurring-stall cause in the tested regime.
4. **Low confidence that ordinary CPU overload, GC, or autosaves explain the recurring ~264 ms tail.** Their measured signatures do not match the sustained outside-callback waits or the VSync contrast. Isolated save hitches remain a separate real issue.

Godot's [Windows stutter guidance](https://docs.godotengine.org/en/stable/tutorials/rendering/jitter_stutter.html) recognizes windowed/driver/VSync effects, but does not diagnose this specific 264 ms pattern. Adaptive and Mailbox VSync are not independent alternatives in Compatibility: Godot [documents them as behaving like Enabled](https://docs.godotengine.org/en/stable/classes/class_displayserver.html#enum-displayserver-vsyncmode).

## Approved experiment 1 result: native render-time instrumentation on/off

The opt-in `--diagnose-native-render-timing` route changed **only** viewport render-time collection in four approximately 10-second windows: on/off/on/off. VSync stayed Enabled and the cap 58 in every measured frame. The initial window reproduced the tail, so the stop-if-absent rule did not fire. The 40.055-second run yielded **1,927 ticks / 0.601×**, p95 **263.76 ms**, **154** frames over 100 ms and **346/346** focused frames. Raw per-frame evidence: [native render-timing control](../../reports/evidence/R0.02a/native-render-timing-control.json).

After discarding the first second of each window:

| Window | Native timing | Frames | >200 ms intervals | Frame p95 |
| --- | --- | ---: | ---: | ---: |
| 0 | On | 84 | 35 | 263.98 ms |
| 1 | Off | 78 | 35 | 265.04 ms |
| 2 | On | 74 | 35 | 263.26 ms |
| 3 | Off | 74 | 34 | 263.98 ms |

The recurrence survives both off windows with essentially unchanged frequency/severity. This **rejects native render-timing instrumentation as the practical explanation** for this laptop's repeated ~264 ms waits. It does not locate the wait within native presentation, driver, compositor, or scheduling code. The diagnostic hook is opt-in; normal project VSync/cap settings were not changed. `dotnet build game/Festival.Game.csproj --no-restore` passed with zero warnings/errors before the run.

## Approved native trace attempt: intermittent fast run

The first non-administrator WPR start failed because the session lacked system-profiling privilege. The user then started `GPU.Light` in an Administrator PowerShell session. The game itself was launched normally with the opt-in diagnostic; the recorder was stopped and saved to [vsync-native-15s.etl](../../reports/evidence/R0.02a/vsync-native-15s.etl), with no recording left active. However, the diagnostic's stop-if-absent rule ended the game after **10.01 seconds**: **0.984×** speed, **18.57 ms** p95, one frame over 100 ms, **564/564** focused frames, VSync Enabled / 58 cap. The initial recurring-stall criterion was false. See [run measurements](../../reports/evidence/R0.02a/vsync-native-trace-run.json). This trace cannot classify the recurring ~264 ms wait because that wait did not recur in the captured run. The fast run reinforces that the failure is intermittent under apparently identical game settings; it does not demonstrate a fix.

The user approved one further bounded capture attempt, limited to three launches. [Retry 1](../../reports/evidence/R0.02a/vsync-native-retry-1.json), [retry 2](../../reports/evidence/R0.02a/vsync-native-retry-2.json), and [retry 3](../../reports/evidence/R0.02a/vsync-native-retry-3.json) all exited under the no-stall rule at approximately 10.01 seconds. Each attained about **0.985×**, had p95 **18–19 ms**, exactly one frame over 100 ms, and all frames focused. `initialStallsReproduced` was false in each. An initial process-lifetime check incorrectly flagged retry 1 as a probable reproduction before its completed JSON was read; this was corrected and subsequent decisions used only the completed measurements. The second WPR session was saved to [vsync-native-retry-2.etl](../../reports/evidence/R0.02a/vsync-native-retry-2.etl) after retry 3. These three runs likewise provide no bad-run native classification.

## Proposed remaining bounded investigation — requires new approval

1. If the user approves another try, obtain **one 10–15-second native scheduling/presentation trace during an actual bad run**. Stop after at least ten long gaps and classify the main thread as blocked in present/driver/event wait, running CPU, or runnable-but-unscheduled. The first authorized capture was fast and therefore non-diagnostic; do not infer that it ruled out native presentation.
2. **Only if the trace points to a mechanism**, try one reversible presentation/window/renderer intervention and at most two fresh 60-second validation launches. Require speed ≥0.95×, p95 ≤25 ms, no recurring >200 ms tail, focused frames throughout, and human camera-motion approval. Stop on first validation failure; do not promote an intermittently passing setting.

Do **not** increase `FoundationClock`'s tick rate or merely replace engine delta with wall time as a performance fix. Either could make the authoritative clock catch up while the player still sees long freezes and delayed input, possibly worsening catch-up bursts. A separate timing-contract review may be justified later, but does not satisfy this frame-pacing gate.
