# S0.08 — rendered preparation performance diagnostic

Status: **Accepted bounded diagnostic after independent review of the six A/B windows and one authorized full-length Release/no-capture run. Diagnosis only; no performance correction implemented.**

## Findings

The earlier approximately 255 ms frame tail did not reproduce in any of six short windows. Exporting Release and removing the per-frame capture path both preserve approximately 1× arrival throughput. The old `Directory.CreateDirectory` call is unnecessary measurement overhead, but its containing capture stage measured only about 0.1 ms/frame here; this evidence does **not** attribute the old severe tail to that call or to Debug.

A distinct smaller hitch is reproducible at finished settlement, tick 39,068: **111.455 ms Debug/capture and 132.296 ms Release/no-capture**, with **94.773 / 115.501 ms** inside the simulation/observation stage. This is the tick that stages, serializes, validates and writes the mandatory finished autosave. Capture work at that Release frame is zero. This identifies the synchronous boundary pipeline as the dominant measured work in those two frames, not a general movement or GPU bottleneck. No async-save correction has been implemented or approved.

The full-length Release/no-capture run confirms near1× throughput and a normal p99 of17.970ms, but also records **one604.054ms wall gap** outside the measured CPU stages. Therefore severe *occasional* stalls survive without Debug or per-frame capture I/O. The prior *frequent*255ms tail is not reproduced, and the604ms gap is not attributed to an engine, OS, driver, GC or thermal cause by this evidence. The bounded investigation stops here.

Optional viewport CPU/GPU timing was enabled in every arm. Instrumentation may itself perturb timing; foreground/minimization, thermal clocks and unrelated OS activity were not traced.

The final full-length arm adds a phase field and one extra observation plus `Any` check per running frame to classify Arrival versus Live. The six archived short-window samples predate that addition. This small but unisolated instrumentation difference prevents an exact apples-to-apples overhead claim between short and full runs; compare broad wall-tail behaviour, not tiny decimal differences. All runs also contain shared in-memory profiling overhead, and viewport timing queries may affect driver pacing.

## Decision and limits

The historic frequent long-run tail remains unresolved; the full run establishes that rare long gaps are not solely Debug/capture artifacts. Neither result justifies a broad movement/render rewrite or lower scene quality. Even otherwise clean windows exceed the strict16.667ms frame budget at the95th percentile, so this is not a stable60FPS acceptance claim. All sampled people completed and the final save is exact, but this does not resolve OS input latency or general population capacity.

The synchronous save pipeline is a concrete, separate source of100–144ms pauses. Do not jump to an async-save redesign from this diagnostic alone: preserving validated candidate durability, failed-write state retention and retry semantics is mandatory. If further investigation is authorized, a single correlated managed/native/OS scheduling trace around a long no-capture run would target the unattributed gap; separately timing boundary clone/serialization/validation/write would constrain any later save correction. No further run, correction, commit or push was performed within S0.08.
