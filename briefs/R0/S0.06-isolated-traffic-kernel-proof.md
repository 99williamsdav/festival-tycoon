# S0.06 — isolated traffic-kernel proof (P3)

Status: **Stopped — P3 not accepted; new repair decision needed** under [S0.03](S0.03-movement-architecture-review.md). See the [S0.06 checkpoint](../results/S0.06.md). P1 and P2 are accepted. This is an executable design proof, **not** production navigation integration, a supported-population claim, or authorization to change queue/gameplay rules. R0.01 remains paused.

## Contract to prove

Build a deterministic, fixed-point traffic kernel outside the current `GameSession` movement path. Each person keeps an individual ID, intent generation, position, speed, route/progress, wait/fairness state and physical occupancy. Preserve the provisional 300 mm minimum centre-to-centre separation as a pairwise measure, not body radius. A tick reads one start state, generates bounded proposals, arbitrates all contested movement, then commits jointly. Every accepted displacement is within that person's speed allowance; terrain and interpersonal swept paths are safe; denied proposals consume neither distance nor route progress. Presentation/observer calls must be absent from decisions.

Model at least one explicit controlled narrow region with entrance, direction, occupancy, safe exit berth and stable request order. An occupant retains physical rights until clear; cancellation releases obsolete future claims without erasing actual occupancy. Opposing continuous demand must get finite-batch service where a feasible exit exists. A blocked exit prevents new entry. For local crossings, consider opposing edges and diagonal sweeps, not only equal destination cells. Do not claim general deadlock freedom from a bounded planner.

Canonical decision state (claims, fairness tickets, intent/region versions, recovery if implemented) must serialize, validate, hash and continue identically after restore. Derived spatial indices may be rebuilt only without changing grants. Define distinct outcomes: completed, pending within bound, unsupported layout, and established infeasibility. A failed bounded search is pending/unresolved, **not** proof that geometry is impossible.

## Minimal adversarial proof suite

Use small explicit fixtures with deterministic bounds derived from geometry, speeds and service times. Cover two-way one-person passage; slow leader/faster follower; occupied exit berth; continuously arriving demand from both sides; perpendicular and diagonal crossing; stationary obstacle; cancellation/retarget during a claim; save→restore→continue with a claimant waiting and another inside; and a service ingress/egress handoff in which completion does not instantly vacate the exit. Include a cyclic conflict with an available refuge and one without a demonstrated solution; for the latter report pending/unsupported rather than inventing a teleport. Assert every-tick speed, terrain sweep, pairwise swept clearance, stable priority and eventual discharge where the fixture is explicitly feasible. Count useful unchanged-intent progress, region discharge and service completion separately from mere lateral movement.

## Boundaries and gates

Do not modify `GameSession.Navigation`, current queue ownership, production save format, `game/Main.cs`, the S0.00 fixture or the 80-tick/second clock. The kernel may live in a separate simulation namespace/module with tests, but no production caller uses it yet. Do not run 100/200/500/1,200 diagnostics or make capacity claims from isolated tests. Document interfaces, state machine, invariants, fixture assumptions, remaining unknowns (especially automatic region extraction and scattered-bay compaction) and what P4 integration would need.

Run targeted kernel tests and one final solution build/full suite after stabilization. One fresh independent reviewer checks proof quality and untested edge cases; allow one focused repair/re-review, then stop and escalate if safety or feasible-fixture completion still fails. No push or R0.01 work.
