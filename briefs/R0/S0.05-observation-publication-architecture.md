# S0.05 — authoritative stepping and observation publication (P2)

Status: **Accepted after independent re-review** under the [S0.03 architecture decision](S0.03-movement-architecture-review.md), after accepted [S0.04 P1](../results/S0.04.md). See the [S0.05 result](../results/S0.05.md). R0.01 remains paused. This stage changes observation cost, not navigation, queue decisions or crowd semantics.

## Outcome

Allow one or many authoritative ticks without automatically constructing a full `SessionSnapshot` and SHA-256 hash on every tick. Keep `AdvanceTicks` and `CaptureSnapshot` compatible for existing callers and explicit verification. Provide a clearly named no-publication stepping path and, if needed, a compact per-person position/queue observation with identities for presentation and diagnostic invariants. No authoritative decision may depend on whether or how often observers request data.

Update the real `game/Main.cs` production tick path and the scale diagnostic runner to use this path where they currently discard the snapshot returned by `AdvanceTicks(1)`. The production presenter may need positions every tick for interpolation, but must not require a full hash for each tick; explicit save, pause, final verification and user-visible diagnostics may still capture a full snapshot at a documented cadence. Do not make a runner-only optimization while leaving the actual game tick loop on the old path. Avoid changing legacy capture-specific verification behaviour without a matching regression check.

## Proof

1. Differentially advance two identical sessions with the same commands and mixed step/publication schedules. Compare event order and payloads, individual positions/routes, queue admission and service, wallets/transactions, canonical hashes and persisted save→restore→continue at common ticks. Include pauses, variable walking speeds, retarget/cancel and one snapshot-free interval covering purchases. Explicit `CaptureSnapshot` must remain canonical and stable.
2. Prove the actual production path uses snapshot-free ticks and bounded presentation observations; demonstrate that the diagnostic runner does too. Preserve every-person validation during timed windows, including identities, queue ownership and failed/completed status; do not weaken checks to get a faster number.
3. Measure P1-versus-P2 100-person representative/congested and second representative seed with identical fixtures, windows and correctness bounds. Report tick mean/p95/p99, snapshot/hash time, allocations/GC and completion tick/hash. Only if correct, run bounded 200 representative/congested headless. Keep old and new measurement paths clearly labelled; do not attribute a changed runner check cost to simulation improvement without explaining it.
4. Run focused tests, one final solution build/full suite, and a proportionate production game smoke check if the executable/tooling is available. No rendered 200 claim or 500/1,200 run.

## Stop and review

One focused repair pass if publication frequency changes authoritative results, save continuation or presentation identity. If still failing, revert P2 and report. A fresh independent reviewer checks API semantics, actual production call path, benchmark fairness and evidence; re-review only repaired findings. No P3 movement integration, R0.01, push, population/tick-rate/fidelity change, or unsupported capacity claim.
