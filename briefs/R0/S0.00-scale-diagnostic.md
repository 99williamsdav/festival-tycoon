# S0.00 — population architecture diagnostic

Status: **Accepted diagnostic.** A bounded 200 representative run completed functionally but missed arrival mean/tail targets; congested 200 produced valid timed windows and then timed out during bounded completion. Rendered was not run. Independent Astra-high review accepted the corrected implementation and truthful evidence. The result recommends a targeted avoidance-routing and snapshot-publication architecture spike; see [the result](../results/S0.00.md). This is not a 100-, 200-, 500- or 1,200-person support claim.

## Question and evidence

Can the current one-world, one-person-per-ticket simulation grow materially beyond 50 while preserving the 80-tick/real-second 1× clock, full identities/wallets, deterministic saved state, physical queues and identical off-camera causality? Read [M1.00](../results/M1.00.md), [M0.10](../results/M0.10.md), [R0 design](../../ROGUELIKE_DESIGN.md), the navigation/queue code and rendered presenter first. M1.00 proves only a 50-attendee shared world. M0.10's 200/500 runs used eight isolated worlds and are warning evidence, not a shared-world limit. R0.00 is accepted but adds no crowd load.

## Bounded probe

1. Make a diagnostic-only, parameterised **single `GameSession`** with 50, then 100, then 200 distinct people and three active physical service destinations. Use a valid representative farm route and a separate congested layout; verify every declared agent is active during timed windows. Keep identities, wallets, queue ownership and collisions. Fixture retargets are explicitly development-only. Do not use eight isolated sessions or merely empty visual agents.
2. Instrument non-overlapping time for route searches, movement/separation, queue updates, snapshot/hash and rendered presentation. Count path searches, expanded nodes, searches triggered by avoidance, queue reassignments, allocations/GC, blocked-agent age and active population. Label categories as measured or inferred; do not double-count them as a total. Profile an arrival period, a congested service period and a late state with accumulated transactions.
3. On the existing declared machine, use bounded, repeatable 1× runs. Report mean/p50/p95/p99 tick cost, attained speed, input/frame pacing if rendered, save/restore identity, completion/correctness and exact build/seed/layout. Repeat key runs across at least two seeds if affordable. Fail fast if 100 shows structural overload; bound 200 and any rendered run with exact-child cleanup. Do not run 500/1,200 yet.
4. Compare 100/200 costs with the current clock's 12.5 ms/tick absolute 1× ceiling and the existing <8 ms/rendered-frame simulation target. The latter requires roughly 6 ms/tick at 60 FPS/80 ticks per real second; aim for spare room as needs/hazards are added. Keep strict 60 FPS and OS input checks separate from simulation throughput. A single average is not a stability claim.

## Deliverable and stop

Write an evidence-backed bottleneck breakdown and recommend one of: (a) a measured targeted architecture spike, such as separating local avoidance from global routing or changing snapshot publication; (b) a broader navigation/presentation replacement with acceptance criteria; or (c) a product-level population tradeoff requiring the user's decision. Explain how each option preserves or changes one person/ticket/wallet, saved determinism, physical access and off-camera behaviour. Estimate the next proof point, not an unsupported final capacity. Do not silently lower the movement clock, aggregate people, remove identities, implement camera-dependent logic, or promise a 1,200-person world. Stop before a production rewrite, gameplay brief R0.01, or scale-target change.
