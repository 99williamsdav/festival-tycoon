# R0.05y — shared queued-service choice

Status: Implemented within bounded automated gate, 29 September 2026; [result and limitations](results/R0.05y-shared-queue-choice.md). Implement only the common multi-instance queue decision behavior; no new art, preparation-HUD work or startup-seed change.

Catalogue: normal Build campaigns can have two free-water taps and two toilets, each with physical queue ownership and more than one instance of the same service. These are the policy's two production adapters. Food and bar each have one instance and different products; they retain their existing fixed-product route and FIFO. The generic `ServiceQueue` is a targeted fixture with explicit queue IDs, not an autonomous multi-instance chooser. Medical first aid, stage, entrance and response posts do not offer interchangeable queued instances. Document this boundary in the result.

One shared decision policy compares candidates in simulation ticks: current-position route walking time + physical members' expected remaining service + plausibly earlier approaching demand + the chooser's own service duration. The owner contributes actual remaining work: current thirst/rate for drinking or `ServiceTicks` for toilet use; other toilets use known visit kind if committed, otherwise the public 3:1 wee/poo expectation (280 ticks), never a future random draw. Approachers do not acquire a remote reservation; only physical arrival changes FIFO. Full, blocked, unreachable and incompatible candidates are excluded, with stable ordinal-ID ties.

Proposed tunables: review every 160 simulation ticks per seeker, staggered by agent ID over eight ticks; switch only for more than 120 ticks of estimated improvement, and only after the same review cooldown. This matches the existing water hysteresis and gives toilets the same policy. Keep route estimation on this bounded simulation cadence, reusing active navigation where possible; no per-frame path scan. Reassess approaching and queued users, forfeiting an old physical place on a switch. Never switch an entering/using/leaving service owner. Persist the toilet review tick in the authoritative immersion state; existing water review state already persists. Retry starts from baseline state.

Verify long-versus-short lines, travel tradeoffs, owner remaining time, multiple approachers, cooldown/margin/no oscillation, in-service ownership, full/unreachable exclusion, same-seed/save-load continuation and individual water/toilet regressions. Script native evidence for both two-toilet and multi-tap decisions, seek independent focused review, commit and create a distinct Windows export. Stop at this boundary before the separately authorized prep bottom bar.
