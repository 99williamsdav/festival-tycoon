# Persistent preparation bar — concept v1

Concept only, returned for coordinator/user review. No runtime implementation commissioned or performed. Image generated with the built-in image-generation tool; final image visually inspected. Prompt and revision recorded in PROMPTS.md.

## Proposal

One bottom-edge dock replaces the previous prep navigation row and separate budget footer. Exactly five labelled pictogram buttons, in order: Build, Programme, Staff, Equipment, Stock. Build is selected in teal. Catalogue appears left, existing readiness summary right. Close the catalogue with X or activate its selected button again; the dock remains. Selecting another button switches the prep panel, never advances an irreversible wizard.

Collapsed-panel state uses this same dock in precisely the same position, with the catalogue absent and no selected panel highlight. No separate screenshot is necessary to define this state. Required-task badges and the budget strip remain. The Before opening card may collapse to its heading with an unresolved count; activating the red reason beside Start reopens it.

The dock persists throughout pre-start, including placement. On festival start it disappears; the approved live HUD is unchanged. The entire preparation dock is restored on editable retry. Do not leave two navigation rows or duplicate budget/Start footers.

## Information and controls

- Upper dock strip: budget, complete draft total, remaining funds, payment timing, Start festival and explicit missing-task reason. Draft total is the full applicable plan, not services alone. Existing accounting and confirmation rules remain authoritative.
- Red exclamation badges indicate actual unmet requirements, not merely unvisited panels. In this example Build, Programme and Staff need attention. Equipment and Stock have no warning simply because optional purchases are unselected.
- Readiness rows use red text plus symbols and specific reasons. Clicking a row opens its relevant setup destination. Preserve actual existing safety/programme/sound checks; the mockup does not invent new blocking rules.
- Start stays visible. Its unavailable reason must remain focusable/readable even if the button itself is disabled. Red is paired with words and an exclamation, never used alone.
- Your Perks, People and Rotate view stay in a visually subordinate group at the dock's right edge. Preserve existing People options and camera inputs. Perks opens the existing display, not a new spending mechanic.
- Icon meanings: Build = hammer/plan, Programme = note/set-list, Staff = crew including hi-vis, Equipment = speaker, Stock = crate/bottle. These are concept graphics, not exported production icon assets. Labels must always remain; tooltips and accessible names repeat action/state.

## 1280 × 720 fit

The generated 1672×941 image is approximately 16:9. At 1280-wide display, the left catalogue is approximately 320 px wide; right readiness about 230 px. Catalogue ends around y550 and dock begins around y577, leaving separation and no overlap. Main buttons are roughly 195 px wide each, with about 295 px for ancillary controls. All five labels fit without truncation. The main map remains visible between side panels.

The generator reduced the dock modestly, but did NOT meet the requested exact 108 px height: the pictured dock occupies roughly 143 px at 720p. Treat the image as a visual direction, not a measured layout spec. Recommended implementation exploration is a 36 px accounting row plus a 72 px icon row (108 px total), with 28–32 px icons, 16 px labels and at least 44 px primary targets. Ancillary controls can use two rows. Do not scale the complete raster down as a UI implementation. If the compact height compromises readable text or focus targets, prefer a slightly taller dock over tiny controls. This exact trade-off remains for review/native layout validation.

Production validation must include 1280×720, keyboard focus, larger text, panel switching, collapsed panels, placement, and start/live transition. No native UI tests have been run for this concept.
